SECTION 1: PROJECT OVERVIEW
────────────────────────────────────────────────────────────────────────────────

Name        : SVCE Education ERP — Phase 0
Institution : Sri Venkateswara College of Engineering (SVCE)
Purpose     : Unified department-level ERP system covering Admin, HOD, and
              Faculty portals for managing students, faculty, attendance,
              assignments, IA marks, activities, meetings, and schedules.

This is a monorepo containing two top-level packages:
  1. unified_backend/    — Express.js REST API server
  2. unified-frontend/   — React Native + Expo app (targets Web, iOS, Android)

Single shared PostgreSQL database: education_erp

The frontend was built by merging three previously separate portals:
  - Admin ERP (Repo 1)
  - HOD Portal (Repo 2)
  - Faculty-Student ERP (Repo 3)
All three portals now live inside one Expo app and share one backend.

SECTION 4: BACKEND ARCHITECTURE
────────────────────────────────────────────────────────────────────────────────

SERVER STARTUP SEQUENCE (server.js)
  1. Load .env via dotenv
  2. testConnection() — ping PostgreSQL, exit on failure
  3. initializeDatabase() — apply unified_schema.sql + all migrations + base seed
  4. app.listen() on config.port (default 5000)
  5. SIGTERM / SIGINT graceful shutdown (pool.end())

EXPRESS APP (src/app.js)
  Middleware stack (in order):
    helmet()                          — security headers
    cors()                            — CORS (origin from CORS_ORIGIN env var)
    rateLimit (global: 1000/15min)    — applied to /api/*
    rateLimit (auth: 50/15min)        — applied to login endpoints
    express.json({ limit: '10mb' })
    express.urlencoded({ limit: '10mb' })
    cookieParser()
    compression()
    morgan("combined") → Winston       — HTTP request logging
    express.static("uploads")         — serves uploaded files at /uploads
    GET /health                        — health check endpoint
    /api → routes/index.js            — all API routes
    notFound + errorHandler           — 404 + error middleware

LAYER PATTERN
  Route → Controller → Service → Repository → pg (raw SQL queries)
  No ORM at runtime. All SQL is written by hand in repository files.

DATABASE BOOTSTRAP (src/config/dbBootstrap.js)
  Runs inside a single transaction:
    1. Execute unified_schema.sql (CREATE TABLE IF NOT EXISTS — idempotent)
    2. Execute all .sql files from database/migrations/ (sorted by filename)
    3. Execute unified_seed_empty.sql (departments, roles, semesters, etc.)
    4. Upsert admin user (username: "admin", password hash hardcoded for seed)
    5. Assign admin role_id to admin user
    6. Insert default settings row for admin
  Safe to re-run on every startup.

JWT CONFIG (src/config/index.js)
  JWT_SECRET auto-generation:
    - If JWT_SECRET is missing or equals the placeholder string, a 64-byte
      hex random secret is generated and written back into .env.
    - This means a fresh clone works without manual .env editing.
  Expiry: JWT_EXPIRES_IN (default "8h")

SECTION 5: AUTHENTICATION & AUTHORIZATION (BACKEND)
────────────────────────────────────────────────────────────────────────────────

LOGIN ENDPOINTS
  POST /api/auth/login              — universal (admin or faculty, auto-detected)
  POST /api/auth/admin/login        — admin-only login
  POST /api/auth/faculty/login      — faculty + HOD login (body: departmentCode, username, password)
  POST /api/auth/logout             — invalidates session (requires token)
  GET  /api/auth/me                 — returns current user profile

TOKEN FORMAT
  Bearer token in Authorization header  OR  "token" cookie
  JWT payload includes: id, username, role, departmentCode, isHOD, roles[]

MIDDLEWARE GUARDS (src/middleware/authenticate.js)
  authenticate         — verifies JWT; sets req.user; blocks if missing/expired
  requireAdmin         — checks req.user.role === "admin"
  requireHOD           — checks req.user.isHOD === true OR roles.includes("HOD")
  requireRole(...slugs) — checks req.user.roles includes any of the given slugs
  requireSameDepartment — checks req.user.departmentCode matches req.targetDepartmentCode
  optionalAuth         — attaches user if token present; does not fail if absent

USER ROLES IN SYSTEM
  admin   — college-level administrator (full access to all departments)
  hod     — Head of Department (faculty with is_hod=true; scoped to own department)
  faculty — Regular teaching faculty (scoped to own classes)

COORDINATOR ROLES (stored in coordinator_assignments table, cached in faculty.coordinator_roles)
  Faculty members can hold named coordinator roles such as:
  SPORTS, CULTURAL, TECHNICAL, HACKATHON, INDUSTRY, etc.
  These are checked via requireRole(...slugs) middleware.

SECTION 6: DATABASE SCHEMA SUMMARY
────────────────────────────────────────────────────────────────────────────────

All tables use BIGSERIAL primary keys and TIMESTAMPTZ for timestamps unless noted.
Cascade convention:
  Master/reference data (departments, semesters, etc.) → RESTRICT on delete
  Ownership rows (attendance, submissions) → CASCADE
  Optional references → SET NULL

SECTION 8: FRONTEND ARCHITECTURE
────────────────────────────────────────────────────────────────────────────────

ENTRY POINT
  src/App.tsx  →  <AuthProvider> wraps <NavigationContainer>
  RootNavigator reads useAuth() to decide which shell to render:
    - Not authenticated            → LoginScreen
    - user.role === "admin"        → AdminPortal
    - user.role === "hod"          → HODPortal
    - user.role === "faculty"      → FacultyPortal
  The `key` prop on each portal is set to `${role}-${userId}` so React
  completely unmounts and remounts the portal on every new login, preventing
  state leaks between sessions.

UNIFIED AUTH CONTEXT (src/context/AuthContext.tsx)
  Persists to AsyncStorage (key: "unified_token" / "unified_user").
  Provides: user, token, isAuthenticated, isReady, login(), logout()
  logout() wipes ALL session keys from all portals simultaneously.
  Global refs:
    getUnifiedToken()     — readable outside React for axios instances
    unifiedLogoutRef      — callable outside React by 401 handlers

AXIOS INSTANCE (src/api/axiosInstance.ts)
  baseURL: process.env.EXPO_PUBLIC_API_URL (default: http://localhost:5000/api)
  request interceptor: attaches Bearer token from tokenStore.getToken()
  response interceptor: on 401, calls triggerLogout() → unifiedLogoutRef.current()
  Returns response.data directly (not the raw Axios response).

PORTAL SHELL PATTERN (same for all 3 portals)
  Each portal has its own:
    - AuthProvider (portal-scoped context)
    - ThemeProvider (portal-scoped dark/light)
    - QueryClientProvider (fresh per mount — prevents cache leak between users)
    - PaperProvider (react-native-paper theming)
  Token Bridge component: copies unified token into portal's own auth state on mount.
  Logout Bridge component: calls unifiedLogout() when portal's own auth clears.

NAVIGATION STRUCTURE

SECTION 14: KEY DESIGN DECISIONS & NOTES FOR AI AGENTS
────────────────────────────────────────────────────────────────────────────────

1.  SINGLE SHARED BACKEND: All three portals (admin, hod, faculty) hit the same
    Express server on port 5000. There is no BFF or gateway.

2.  ROLE DETERMINATION ON LOGIN:
    - Admin: POST /auth/login with only username + password
    - HOD:   POST /auth/faculty/login + expects isHOD=true in response
    - Faculty: POST /auth/faculty/login + isHOD=false
    The unified LoginScreen handles this via the role tab selection.

3.  PORTAL ISOLATION:
    Each portal (admin/hod/faculty) has its own AuthContext, ThemeContext, and
    QueryClient. They are independent React subtrees. Cross-portal communication
    only goes through the top-level UnifiedAuthContext.

4.  TOKEN BRIDGE PATTERN:
    On portal mount, a TokenBridge component reads the unified token from
    UnifiedAuthContext and injects it into the portal's own AuthContext and
    AsyncStorage. This is needed because each portal was originally a standalone
    app with its own auth flow.

5.  NO GLOBAL STATE LIBRARY:
    Admin portal uses React Context + React Query.
    HOD and Faculty portals use Zustand (for persistent portal-level state)
    + React Query for server state. Check context/hod/ and context/faculty/ for Zustand stores.

6.  CLASS IS THE CENTRAL ENTITY:
    The `classes` table links subject + section + faculty + academic_year.
    Attendance, IA marks, and assignments all key off class_id ONLY.
    Subject name, faculty name, section name are always derived via JOIN to classes.

7.  IA MARKS AVERAGE IS DATABASE-COMPUTED:
    ia_marks.average is a GENERATED ALWAYS ... STORED column. Never write to it
    from application code. It auto-updates when ia1/ia2/ia3 change.

8.  COORDINATOR ROLES ARE DUAL-STORED:
    faculty.coordinator_roles (VARCHAR, comma-separated) = denorm cache for fast read.
    coordinator_assignments table = authoritative source.
    When assigning/removing roles, update BOTH.

9.  MEETING SOFT DELETE:
    Deleting a meeting sets status='deleted' and deleted_at=NOW().
    The row is retained for audit trail. Filter out deleted meetings with
    WHERE status != 'deleted' in queries.

10. SCHEDULES ARE PRIVATE:
    All schedule queries must include WHERE user_id = <logged_in_user_id>.
    The backend enforces this — the user cannot pass a different user_id.

11. DATABASE MIGRATIONS MUST BE IDEMPOTENT:
    All new migration SQL must use CREATE TABLE IF NOT EXISTS,
    ADD COLUMN IF NOT EXISTS, CREATE INDEX IF NOT EXISTS, etc.
    dbBootstrap.js runs all migrations on every server startup.

12. JWT SECRET PERSISTENCE:
    The first time the server starts without a JWT_SECRET, it generates one and
    writes it back to .env. Do not delete .env during development or all active
    sessions will be invalidated.

13. UPLOADS DIRECTORY:
    Files are stored at unified_backend/uploads/ on the server filesystem.
    They are served at http://localhost:5000/uploads/<filename>.
    No cloud storage (S3, etc.) is used in Phase 0.

14. AI CHECKER:
    The /ai-checker endpoint requires an OPENAI_API_KEY. Without it, the feature
    is silently unavailable. This is an optional feature and not required for
    core functionality.

15. FEE MODULE:
    Most fee sub-screens (TuitionFee, ExamFee, TransportFee, HostelFee) are
    placeholder stubs that display "Coming soon." Only AcademicFee is implemented.

16. PRISMA IS TOOLING-ONLY:
    prisma/schema.prisma exists for `prisma studio` (database browsing) and
    `prisma validate`. The runtime queries all use node-postgres (pg) directly.
    Prisma is NOT used as the ORM for actual API calls.
